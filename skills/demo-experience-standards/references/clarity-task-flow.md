# Clarity and task flow

Simon approved adding this guidance on 26 November 2026 after reviewing a screenshot of design principles. Use the principles that help the audience's task when composing or refining demo websites, presentations and Voice Demo Builder interfaces. These are design prompts, not guarantees of behaviour or a requirement to apply every named effect. Preserve the owning specialist's controls, state, evidence and release process.

## Make the task easy to follow

| Principle | Authoring choice | Example and boundary |
| --- | --- | --- |
| Progressive disclosure | Lead with the common task; reveal advanced or occasional choices through clear labels. | Keep optional configuration behind a useful settings control; put presentation exploration in backup. Keep essential conditions, errors and the next action visible. Retain complete reading and static content. |
| Recognition over recall | Keep relevant context and choices available where people act. | Show the selected client and scenario, offer source-supported caller questions, and retain useful selections on return. Use labelled controls instead of unexplained icons. Visibility belongs to the current task; it need not put every setting on screen. |
| Proximity, common region and similarity | Use spacing and consistent treatment to show what belongs together and what behaves alike. | Place each fact beside its source and correction actions. Keep field errors near their fields. Check the relationships after mobile reflow. Use containers where they explain a group, rather than wrapping every element in a card. |
| Cognitive load and Tesler's law | Let the system carry routine complexity while keeping meaningful decisions understandable. | Reuse still-valid, verified configuration and show a concise review before a consequential action. Keep important choices editable. Simplifying a screen must not silently change a target, permission or provider binding. |
| Von Restorff effect | Reserve a distinct emphasis for the action or story moment that most deserves attention. | Distinguish the primary task from supporting links; use scale, placement or contrast for a key resolution. Avoid making every card equally prominent or relying on colour alone. This does not require extra motion. |
| Peak-end rule | Give the story a tangible moment of help and an ending that explains the outcome and next step. | Return to the customer's resolved need and the agent's contribution before a focused next decision. In a task flow, explain what actually happened and what remains. Retain the native return path from a full demo. |
| Goal-gradient effect | Make meaningful completed work and remaining work understandable when a task has stages. | Show which build checks passed and which still need attention. Use real state for progress, expose failures and allow recovery. Do not invent percentages, manufacture urgency or let a finished animation unlock a call. |

For presentations, visible context can be a brief reminder at a handoff rather than a permanent application header. Keep stage copy light. For customer websites, show the customer's task rather than presenter architecture. For Voice Demo Builder, verified readiness remains authoritative. Choose the treatment for that surface instead of copying one layout across all three.

## Check usability separately from appearance

The aesthetic-usability effect is a reason to separate visual approval from task evidence. A polished composition can receive positive feedback while a person still struggles to use it. Inspect what the person can find, understand and complete; do not treat praise for the styling as a passed task check.

Use the relevant questions in the existing final review:

- Can someone identify the next action and the context it applies to without recalling a previous screen?
- Do labels, spacing and emphasis explain relationships at narrow widths and enlarged text, with keyboard focus visible?
- Can occasional detail be found when needed, while essential conditions, errors and decisions stay discoverable?
- Do progress, success, failure and the ending describe actual state, with a useful return or recovery route?
- Can the audience follow the human story and concrete outcome without presenter notes, including the complete static or reading version?

Record material changes and review limits in the existing private operator handoff. Distinguish an author walkthrough from observed use by another person. This reference adds no new approval gate, fixed review score or runtime feature; report user acceptance only when it was observed.

## Select principles with judgement

Keep the screenshot's other ideas as optional prompts when a specific problem calls for them. Pareto is not evidence that a particular 20% of features serves 80% of this audience. Parkinson's law does not justify artificial deadlines. Do not use Zeigarnik or goal-gradient ideas to create nagging unfinished tasks, or defaults to take an unrequested action. Simplification should retain the detail people need to decide and recover.
